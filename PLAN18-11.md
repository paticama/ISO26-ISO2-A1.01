## 1. Basic rules

- We do **not** split work by actor. Use cases are assigned so that each person works with several actors and modules, and nobody implements use cases of the actor they used to lead.
- Each person is assigned one or more use cases per iteration and **owns its complete RADIT cycle**:
  - **R & A:** interaction flows and behavioural diagrams of the use case.
  - **D:** public interfaces and DTOs in `sescam-common`.
  - **I:** server endpoint/service and client view.
  - **T:** unit and integration tests (JUnit 5 + Mockito).
- Every use case raises the version of **one** Maven module (its titular module).
- **Mandatory peer review:** nobody merges into `develop` directly. Each PR is reviewed by another teammate, who checks that it builds cleanly and approves it.
- **Module owner** (support role): each module has one person who reviews the PRs that touch it, checks that changes to its interfaces in `sescam-common` do not break other modules, and tags its releases. The owner does **not** design the interfaces of other people's use cases.

Roles that stay from `PLAN.md`: Patricia is coordinator (planning, repository administration, this plan); Åsta is secretary (decisions and minutes); Victoria keeps the Wiki.

This replaces the 8 domain modules of `modulos.txt` and of `PLAN.md` (patients and schedules are no longer inside admissions). Side benefits: admissions no longer carries 33% of the hours, and there is no cycle between orders and admissions (orders needs patients, which now live in `patients`).

Modules not built yet are replaced by no-op implementations.

## 6. Weekly cadence

Every one-week iteration runs the five disciplines on its use cases and ends with a tagged build that passes its tests.

| Days | Discipline | Output |
|------|-----------|--------|
| Sat–Sun | Planning + Analysis | Issues on the Kanban board, branches, analysis class and interaction diagrams |
| Mon–Tue | Design | Interfaces and DTOs in `sescam-common`; design class and sequence diagrams (PlantUML) |
| Wed | Team meeting | Review `sescam-common` changes, change requests, minutes → issues |
| Wed–Thu | Implementation + Testing | Server and client code, JUnit 5 + Mockito tests |
| Thu–Fri | Look-ahead Analysis | Whoever finishes early analyses next iteration's use cases |
| Fri | Release | PR reviews, `develop` → `main`, tags, configuration audit, actual vs estimated hours, retro |

**Fixed time-box:** the week never stretches. An unfinished use case moves to the next iteration by a decision recorded in the minutes.

## 7. Definition of Done (copy into every issue)

- **Analysis:** interaction flows and behavioural diagrams of the use case; entities placed in their module.
- **Design:** interfaces and DTOs in `sescam-common`; design diagrams committed.
- **Implementation:** server slice and client slice done; module passes `mvn verify`; modules not built yet covered by no-op implementations.
- **Testing:** one test per acceptance criterion, at least one test per alternative flow, unit and integration tests with JUnit 5 + Mockito, JaCoCo ≥ 80% for the module.
- **Security and safety:** role check and audit entry on every clinical-data access; examination safety constraints checked (NFR-05, NFR-11).
- **Close:** RADIT boxes ticked in the spec and the issue, actual hours logged, PR approved by another teammate, module version bumped.

## 8. Issues and branches

For each use case, 1 parent issue and 2 sub-issues:

- `UC-PHY-01 – Order and prescribe diagnostic procedure (C4 v1.0.0)` – parent: functional specification, pre/postconditions, acceptance criteria
- `UC-PHY-01 – server (C4 v1.0.0)` – domain entity, service in the module, REST controller in server-app, JUnit tests
- `UC-PHY-01 – client (C4 v1.0.0)` – view in client-app, REST client, form validations

Every issue includes: objective, RADIT disciplines, components involved, contracts/interfaces, acceptance criteria (Definition of Done), estimated hours with and without AI.

Branches (Git Flow; one per slice, with module and version in the name as the course asks). These replace `feature/UC-<ACTOR>-<NN>-<short-name>` from `PLAN.md`:

- `feature/orders-1.0.0-PHY-01-server`, `feature/orders-1.0.0-PHY-01-client` → PR into `develop`
- `release/it1`, `release/it2`, … → merged into `main`, with one tag per module version (format from `PLAN.md`: `<module>-vX.Y.Z`, e.g. `sescam-orders-v1.0.0`)
- `hotfix/<short-name>` stays as in `PLAN.md`.
- No direct commits to `main` or `develop`.
