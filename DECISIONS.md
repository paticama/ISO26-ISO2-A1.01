## 1. Introduction and Document Purpose

This document serves as the **centralized, formal log of architectural, methodological, and configuration decisions (Architecture Decision Records - ADRs)** for the development of the *Comprehensive Management System for Radiodiagnostics and Medical Imaging for the Castilla-La Mancha Health Service (SESCAM)*.

### 1.1. Pedagogical and Operational Context
In compliance with the course syllabus for *Software Engineering II (v1.15.3)*, software development is governed by the **Unified Software Development Process (UP)** and disciplined software engineering methodologies—specifically Software Configuration Management (SCM), Software Quality Assurance (SQA), RADIT engineering disciplines, verification/testing, and maintenance—augmented by Artificial Intelligence techniques and tools (**AI4SE - Artificial Intelligence for Software Engineering**).

### 1.2. Role of `DECISIONS.md` within the Agentic Workflow (Spec-Driven Development)
This file is explicitly designed as an **agent-ingested configuration file** intended for consumption by automated developer agents and Large Language Models (VS Code, GitHub Copilot Chat, Antigravity, OpenCode, Claude Code, etc.). Its primary objectives are:
1. **Eliminate "Vibe Coding":** Prevent undisciplined, non-deterministic, or arbitrary code generation that diverges from formal engineering requirements.
2. **Establish Architectural Guardrails:** Ensure that any scaffolding, boilerplate generation, or contract implementation generated by an AI agent strictly conforms to the established architectural baseline, contractual interfaces, and technical constraints prescribed by the human engineering team.
3. **Guarantee Traceability and Quality:** Formally bind each design decision to use cases, functional and non-functional quality requirements (ISO/IEC 25010), GitHub Issues, and collaborative team meeting minutes.

### ADR-001: Adoption of the Unified Process (UP) and Spec-Driven Development

- **Status:** Accepted
- **Date:** 2026-10-17
- **Stakeholders:** Engineering Team ISO26-ISO2-A1.01

#### Context and Problem Statement
The SESCAM system encompasses an intricate clinical domain involving multi-modality radiological examinations, RIS/PACS integration, scheduling workflows, clinical triage, and preparation protocols. A disciplined software development methodology is required to maintain predictability, rigorous engineering governance, and total traceability, while preventing fragmentation and technical debt induced by unguided generative AI code synthesis.

#### Decision
1. Adopt the **Unified Software Development Process (UP)** as the core methodological framework, adhering strictly to its three defining tenets:
   - **Use-Case Driven:** Functional requirements and clinical stakeholder value guide all modeling, architectural design, implementation, and verification activities.
   - **Iterative and Incremental:** The project lifecycle progresses through formal phases (Inception, Elaboration, Construction, Transition) structured into distinct, time-boxed development iterations.
   - **Architecture-Centric:** Software architecture serves as the formal boundary and development guardrail, directing system evolution and scoping AI agent interventions.
2. Enforce the baseline **1:1 heuristic** prescribed by the teaching faculty for initial scheduling:
   - 1 Functional Requirement (FR) $\leftrightarrow$ 1 Use Case (UC).
   - 1 Use Case is realized within one and only one development iteration.
   - *Architectural Evolution:* While this heuristic provides a clean baseline for temporal and budgetary estimations, actual software construction must partition the system into cohesive, loosely coupled architectural modules guided by SOLID design principles, actively avoiding degrading the UP into a pseudo-waterfall sequence.
3. Lifecycle Phase Partitioning:
   - **Iteration 0 (Inception Phase):** Architectural baseline definition, repository configuration, SCM/SQA plan formulation, domain analysis, initial budgeting (€1,000 baseline human resource cost), and milestone scheduling.
   - **Intermediate Iterations 1 to $N-1$ (Elaboration & Construction Phases):** Progressive implementation of prioritized use cases, creation of dedicated Maven submodules, and automated unit/integration testing.
   - **Iteration $N$ (Transition Phase):** Multi-module system integration, comprehensive regression testing, deployment packaging, user manual authoring, and project post-mortem analysis (€2,000 baseline human resource cost).

#### Consequences
- **Positive:** High predictability, systematic elimination of "vibe coding", transparent synchronization between functional specifications and verifiable deliverables.
- **Risks & Mitigations:** The 1:1 heuristic carries the risk of encouraging monolithic design; this is mitigated by enforcing interface-driven decoupling and independent Maven submodules.

#### AI Agent Guardrails
- *The AI agent MUST NOT generate implementation code that is not tied to a formal Use Case explicitly assigned to the current iteration.*
- *The AI agent must respect the branching and delivery milestones defined for the active iteration.*

### ADR-002: Human-AI Governance: Man-in-the-Loop Principle and Responsibility Contracts

- **Status:** Accepted
- **Date:** 2026-10-17
- **Stakeholders:** Engineering Team ISO26-ISO2-A1.01

#### Context and Problem Statement
Integrating generative AI tooling (GitHub Copilot Chat, Antigravity, Claude Code, and reasoning LLMs) dramatically increases implementation velocity. However, allowing autonomous agents to make unguided technological choices introduces severe risks of architectural divergence, package hallucination, and abandonment of software engineering rigor.

#### Decision
1. Ratify the foundational engineering principle of the course:
   > **«The Engineer designs the Interfaces; the AI implements the Contracts.»**
2. Institute a rigorous **RACI Responsibility Matrix** delineating duties between Human Engineers and Automated AI Agents:

| Activity / RADIT Discipline | Human Engineer | AI Agent | Agreed Operational Protocol |
| :--- | :---: | :---: | :--- |
| **Requirements Elicitation & Domain Analysis** | **Accountable** | Informed | Exclusively governed by human engineers through domain analysis of the SESCAM specification. |
| **Use Case Prioritization & Project Scheduling** | **Accountable** | Assistant | Humans establish timelines, budgets, and workload allocation; AI may provide comparative effort estimates. |
| **Architectural Design & Java Interface Definition** | **Accountable** | Auditor | Human engineers design public interfaces, method signatures, DTOs, and exception models. AI audits completeness. |
| **Unit & Integration Test Suite Design** | **Accountable** | Assistant | Human engineers specify test scenarios, boundary conditions, edge cases, and verification oracles. |
| **Boilerplate Implementation & Contract Coding** | Auditor / Reviewer | **Responsible** | AI synthesizes concrete classes and boilerplate fulfilling pre-specified interface contracts. |
| **Code Inspection & Pull Request Review** | **Accountable** | Assistant (Linter) | No automated merging permitted. Mandatory peer review and sign-off by a human engineer. |
| **Ultimate Delivery & Academic Accountability** | **100% Human** | 0% | Full legal, academic, and professional accountability rests solely on the human engineering team. |

#### Consequences
- **Positive:** Preserves engineering discipline and critical thinking, mitigates LLM optimism bias, and guarantees architectural integrity.
- **Risks & Mitigations:** Potential latency during human review; mitigated by optimizing prompt specificity, using standard test fixtures, and enforcing automated verification scripts.

#### AI Agent Guardrails
- *The AI agent is STRICTLY PROHIBITED from modifying the signature of agreed public interfaces without explicit, documented human authorization within a GitHub Issue.*
- *Every concrete class generated by the AI must implement an interface pre-designed by the human engineer.*

### ADR-003: Decoupled Multi-Tiered Architecture and Interface-Oriented Design

- **Status:** Accepted
- **Date:** 2026-10-17
- **Stakeholders:** Engineering Team ISO26-ISO2-A1.01

#### Context and Problem Statement
Past academic cohorts exhibited recurring architectural failures caused by concrete class-oriented programming rather than interface-driven design, resulting in tightly coupled monolithic spaghetti code that made multi-module integration impossible. The system must support heterogeneous clients (desktop, mobile, and web with DICOM viewers) and integrate with external hospital services.

#### Decision
1. Implement a **Multi-Tiered Service-Oriented / Hexagonal (Ports & Adapters)** architectural style with strict layer segregation:
   - **Presentation Layer / API (`presentation` / `controllers`):** RESTful controllers and UI adapters interfacing with desktop, mobile, and web clients.
   - **Application / Service Layer (`application` / `services`):** Orchestrates clinical use cases (e.g., `ScheduleAppointmentService`, `DiagnosticReportService`).
   - **Domain Layer (`domain` / `model`):** Pure clinical business entities (Patient, DiagnosticOrder, RadiologicalProcedure, DiagnosticReport, Appointment, Modality) decoupled from frameworks or persistence mechanics.
   - **Infrastructure / Persistence / Integration Layer (`infrastructure` / `adapters`):** Repository implementations, DICOM connectors, HL7/FHIR adapters, and SSO authentication clients.
2. **Strict Interface-Driven Decoupling:**
   - The presentation and application layers communicate strictly through Service Interfaces and Data Transfer Objects (DTOs).
   - The domain layer defines Repository Interfaces and Outbound Ports; their concrete implementations reside strictly in the infrastructure layer (Dependency Inversion Principle).
3. **Canonical Java Packaging Structure:**
   - Every module must maintain strict package separation:
     - `es.uclm.esi.sescam.[module].api`: Contains public interfaces, DTOs, and domain-specific business exceptions.
     - `es.uclm.esi.sescam.[module].internal`: Concrete implementation classes, package-private wherever feasible.

#### Consequences
- **Positive:** High cohesion, loose coupling, effortless mocking in unit tests, and seamless interchangeability of infrastructure adapters without modifying clinical business logic.
- **Risks & Mitigations:** Increased number of initial interface files; fully justified by adherence to SOLID engineering principles.

#### AI Agent Guardrails
- *Controllers and presentation classes MUST NOT instantiate concrete service classes using the `new` operator; all dependencies must be injected via their corresponding interfaces.*
- *Domain entities must remain free from framework-specific persistence annotations or network transport dependencies.*

### ADR-005: Multi-Module Architecture with Apache Maven and SemVer Governance

- **Status:** Accepted
- **Date:** 2026-10-17
- **Stakeholders:** Engineering Team ISO26-ISO2-A1.01

#### Context and Problem Statement
Treating the codebase as a single monolithic flat project leads to catastrophic merge conflicts, dependency bloat, and violates the incremental delivery model of the Unified Process. Components must be modularized and versioned according to *Maven by Example (Chapter 6)*.

#### Decisión
1. Establish a **root multi-module Apache Maven architecture**:
   - A root `pom.xml` managing global dependency versions (`<dependencyManagement>`), build plugins (`<pluginManagement>`), and declaring all active submodules (`<modules>`).
2. Decompose the SESCAM system into decoupled submodules aligned with functional clinical domains:
   - `sescam-parent` (Root POM).
   - `sescam-common`: Shared domain primitives, common DTOs, cross-cutting exceptions, and utilities.
   - `sescam-core-catalogue`: Catalogue of examination types, modalities, preparation guidelines, contrast protocols, and safety constraints.
   - `sescam-patient-mgmt`: Demographic patient registration, modification, discharge, and satisfaction surveys.
   - `sescam-order-entry`: Diagnostic procedure ordering, clinical justifications, priority tiers, and periodic follow-up surveillance rules.
   - `sescam-scheduling`: Resource/room allocation, medical staff scheduling, slot booking, rescheduling, and waitlist management.
   - `sescam-execution-reporting`: Procedure execution logging, operational incidents, and diagnostic reporting with image linkage.
   - `sescam-integration-dicom`: DICOM interoperability services, PACS connectors, and medical image metadata handling.
   - `sescam-integration-hl7fhir`: HL7 v2 and FHIR adaptors for hospital EHR (HCE) and central admission systems.
   - `sescam-security-audit`: SSO integration, RBAC enforcement, and immutable clinical audit logging.
3. **Semantic Versioning 2.0.0 (SemVer):**
   - Each module's release adheres strictly to `MAJOR.MINOR.PATCH`:
     - `MAJOR`: Breaking changes in public interface contracts.
     - `MINOR`: New backwards-compatible functionality (realization of a new use case).
     - `PATCH`: Backwards-compatible bug fixes and internal refactorings.
   - Intermediate development iterations use `-SNAPSHOT` designations until stabilized on a release branch.

#### Consequences
- **Positive:** Clean dependency graph, isolated component testing, incremental build times, and direct traceability to project delivery milestones.
- **Risks & Mitigations:** Initial configuration overhead; mitigated by establishing standardized parent POM templates.

#### AI Agent Guardrails
- *The AI agent must NOT add arbitrary third-party dependencies to individual submodule POMs without declaring them in the root `<dependencyManagement>` section.*
- *Circular dependencies between Maven submodules are strictly forbidden.*

### ADR-006: Software Configuration Management: Git Flow and Peer-Reviewed Pull Requests

- **Status:** Accepted
- **Date:** 2026-10-17
- **Stakeholders:** Engineering Team ISO26-ISO2-A1.01

#### Context and Problem Statement
Unit 2 (Software Configuration Management - SCM) requires a formal configuration management plan prohibiting direct commits to mainline branches and ensuring that all codebase evolution is audited through peer-reviewed Pull Requests with complete traceability.

#### Decision
1. Enforce the **Git Flow** branching model:
   - `main`: Production/milestone branch containing stable, tagged release deliveries (e.g., `v0.1.0`, `v1.0.0`). Direct commits are strictly prohibited.
   - `develop`: Central continuous integration branch reflecting latest stable developments for the next milestone. Direct commits are strictly prohibited.
   - `feature/CUxx-[short-name]`: Dedicated feature branches branched from `develop` for realizing a specific use case, merged back into `develop` via Pull Request.
   - `release/vX.Y.Z`: Stabilization branches branched from `develop` prior to an evaluation milestone.
   - `hotfix/vX.Y.Z`: Urgent patch branches branched from `main`.
2. **Integration and Peer-Review Policies:**
   - **Direct Push Ban:** Enforced branch protection rules on `main` and `develop`.
   - **Mandatory Pull Requests:** All integrations into `develop` must occur via Pull Requests.
   - **Human Peer Review:** Every PR requires documented review and approval from at least one peer human engineer, verifying:
     1. Clean Maven build and test passage (`mvn clean test`).
     2. Adherence to pre-established interface contracts.
     3. Comprehensive unit test coverage for new functionality.
     4. Direct linkage to the originating GitHub Issue.
3. **Conventional Commits Standard:**
   - Commit messages must follow the structured format: `<type>(<scope>): <subject>`  
     (Allowed types: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`).

#### Consequences
- **Positive:** Clean, audit-ready commit history, zero disruption to mainline integration, and clear contribution evidence via GitHub Insights.
- **Risks & Mitigations:** Branch merge overhead; mitigated by keeping feature branches tightly scoped to a single use case.

#### AI Agent Guardrails
- *The AI agent MUST NEVER execute `git push origin main` or `git push origin develop` directly.*
- *All code produced by an AI agent must reside on an isolated `feature/...` branch and be submitted via a Pull Request.*

### ADR-007: Healthcare Interoperability and Medical Imaging Standards (DICOM, HL7, FHIR, SSO)

- **Status:** Accepted
- **Date:** 2026-10-17
- **Stakeholders:** Engineering Team ISO26-ISO2-A1.01

#### Context and Problem Statement
The SESCAM system must integrate with central hospital infrastructure across Castilla-La Mancha: Corporate Single Sign-On (SSO), Electronic Health Records (EHR / HCE), Admission Systems (BDU), and departmental RIS/PACS platforms.

#### Decision
1. **Adoption of Healthcare Interoperability Protocols:**
   - **DICOM (Digital Imaging and Communications in Medicine):** Handles radiological image storage, query/retrieve (C-FIND, C-MOVE), and web-based image streaming using DICOMweb (WADO-RS, QIDO-RS) to support zero-footprint web viewers.
   - **HL7 v2 & FHIR (Fast Healthcare Interoperability Resources):** Standard structured clinical data exchange:
     - `Patient` resource: Synchronizes demographic and admission records.
     - `ServiceRequest` resource: Models diagnostic imaging orders and clinical justifications.
     - `Appointment` resource: Synchronizes slot bookings, cancellations, and reschedulings.
     - `DiagnosticReport` resource: Transmits structured diagnostic findings and physician reports.
   - **Corporate SSO (OAuth2 / OpenID Connect / SAML):** Governs unified healthcare professional authentication and secure patient access.
2. **Anti-Corruption Layer (ACL) Pattern:**
   - The internal domain model must remain clean and isolated from raw external protocol data structures. Dedicated adapter classes in the integration submodules translate between external DTOs/messages and internal domain entities.

#### Consequences
- **Positive:** Seamless interoperability with standard hospital information systems and compliance with digital health regulations.
- **Risks & Mitigations:** Complex local testing without production hospital systems; mitigated by creating mock server stubs for RIS/PACS, HCE, and FHIR endpoints.

#### AI Agent Guardrails
- *Domain and application layers MUST NOT directly parse raw HL7 pipe-delimited strings or low-level DICOM tags outside of the dedicated integration adapters.*
- *Integration adapters must implement generic interfaces defined in the application or domain layers.*

### ADR-008: Security, Role-Based Access Control (RBAC), Clinical Audit Trails, and Privacy

- **Status:** Accepted
- **Date:** 2026-10-17
- **Stakeholders:** Engineering Team ISO26-ISO2-A1.01

#### Context and Problem Statement
Healthcare data constitutes Special Category Personal Data under European and Spanish legislation (GDPR Article 9, LOPDGDD, Patient Autonomy Act 41/2002, and National Security Framework - ENS). The specification identifies four core user roles and mandates exhaustive auditing of clinical data access.

#### Decision
1. **Role-Based Access Control (RBAC):**
   - **Role 1 - Patient Users (Base Role):** Appointment inquiry, rescheduling requests, cancellations, notifications, historical procedure access, incident reports, and satisfaction surveys.
   - **Role 2 - Physician Users:** Ordering diagnostic examinations (with indication, justification, and urgent/preferential/routine priority), scheduling recurring follow-ups, managing order status, authoring/signing diagnostic reports with DICOM image viewing, and logging execution incidents.
   - **Role 3 - Administrative / Admissions Personnel:** Demographic management, master appointment slot allocation, daily worklist scheduling, waitlist triage, and operational reporting.
   - **Role 4 - System Administrators:** System parameters, catalogue configuration, role/permission management, clinical audit review, and hospital integration configuration.
2. **Immutable Clinical Audit Trail:**
   - Every read, query, DICOM image retrieval, appointment modification, or report signature must generate an immutable audit log record containing: `timestamp`, `userId`, `userRole`, `actionType`, `patientIdAffected`, `resourceId`, `ipAddress`, and `outcome`.
3. **Cryptographic Protection:**
   - Mandatory TLS 1.3 for all communications in transit.
   - Strong encryption (AES-256) for stored sensitive health data and patient identifiers.

#### Consequences
- **Positive:** Legal compliance with medical privacy laws, forensic traceability of clinical access, and clear principle of least privilege.
- **Risks & Mitigations:** Audit logging latency on read queries; mitigated by asynchronous, non-blocking event-driven audit logging.

#### AI Agent Guardrails
- *No API endpoint or service method handling patient records or diagnostic reports may be exposed without role-based authentication and authorization checks.*
- *AI agents must NEVER log unmasked Personally Identifiable Information (PII) or sensitive diagnostic notes in application log streams.*

### ADR-009: Software Product Quality Management Grounded in ISO/IEC 25010

- **Status:** Accepted
- **Date:** 2026-10-17
- **Stakeholders:** Engineering Team ISO26-ISO2-A1.01

#### Context and Problem Statement
Unit 3 of the course requires systematic elicitation and derivation of functional and non-functional requirements grounded in software product quality attributes (*Quality by Design*) compliant with ISO/IEC 25010, alongside actionable verification procedures.

#### Decision
Prioritize and operationalize the critical ISO/IEC 25010 product quality characteristics tailored to the SESCAM radiodiagnostics domain:

1. **Functional Suitability:** Complete realization and clinical correctness of requirements for all four user roles and examination catalogue management.
2. **Security:** Confidentiality, integrity, non-repudiation of signed reports, authentic access via SSO, and immutable access tracking.
3. **Reliability:** High fault tolerance and continuous availability (essential for handling emergency STAT requests from hospital ER departments).
4. **Compatibility (Interoperability):** Strict compliance with DICOM, HL7, and FHIR protocols in all external integration boundaries.
5. **Maintainability:**
   - **Modularity:** Enforced through decoupled Maven submodules and clean architectural layering.
   - **Testability:** Each service component must be accompanied by an isolated unit test suite targeting an automated code coverage threshold of $\ge 80\%$ on business logic.
   - **Analyzability & Modifiability:** Adherence to SOLID principles, minimal cyclomatic complexity, and disciplined package naming.
6. **Usability:** Streamlined clinical workflows for physicians, clear appointment scheduling interfaces for patients, and accessibility across devices.
7. **Portability:** Cross-platform support for heterogeneous clients (Desktop, Mobile, Web) backed by standard Java runtime environments.

#### Consequences
- **Positive:** Seamless alignment with the theoretical Software Quality Assurance (SQA) Plan deliverable and robust continuous verification.
- **Risks & Mitigations:** Continuous quality monitoring effort; mitigated by incorporating automated static analysis and JUnit verification into build routines.

#### AI Agent Guardrails
- *All generated service logic must be designed for testability, permitting dependency injection of mocks or stubs without requiring live database connections.*
- *The AI agent should accompany any newly generated service class with corresponding unit tests using JUnit and Mockito.*

### ADR-010: Bidirectional Traceability: Meeting Minutes, GitHub Issues, Projects, and RADIT

- **Status:** Accepted
- **Date:** 2026-10-17
- **Stakeholders:** Engineering Team ISO26-ISO2-A1.01

#### Context and Problem Statement
The laboratory practicum mandates complete operational traceability. All collaborative team decisions, assigned tasks, and incremental deliverables must map directly from meeting minutes to GitHub Issues, tracked upon an ad hoc GitHub Projects Kanban board.

#### Decision
1. **Mandatory Traceability Chain:**
   $$\text{Meeting Minutes (Wiki)} \longrightarrow \text{Ratified Decision} \longrightarrow \text{GitHub Issue} \longrightarrow \text{Feature Branch} \longrightarrow \text{Commit / PR} \longrightarrow \text{Merge into Develop}$$
2. **Structured GitHub Issue Template (Use Case):**
   Every use case issue must be instantiated from `.github/ISSUE_TEMPLATE/use-case.md` and explicitly include:
   - Title: `CUxx – [Use Case Name] (module vX.Y.Z)`
   - Functional Mapping: Use Case $\leftrightarrow$ Functional Requirement $\leftrightarrow$ UP Phase $\leftrightarrow$ Maven Submodule.
   - Hyperlink to the team meeting minutes on the GitHub Wiki.
   - **RADIT Disciplines Checklist:** Requirements, Architecture, Design, Implementation, Testing.
   - Formal Contracts and Interfaces involved.
   - Acceptance Criteria (**Definition of Done - DoD**).
   - **Comparative Effort Estimation (in hours):** Estimated effort **with AI assistance** contrasted against estimated effort **without AI assistance**.
   - Direct cross-reference to relevant Architecture Decision Records in this `DECISIONS.md`.
3. **GitHub Projects Kanban Board:**
   - Workflow columns: *Backlog / Todo $\rightarrow$ In Progress $\rightarrow$ In Review (PR) $\rightarrow$ Done*.
   - A task moving to *In Review* must be paired with an active Pull Request.

#### Consequences
- **Positive:** Full transparency for academic continuous evaluation, verifiable effort accounting, and empirical demonstration of AI productivity gains.
- **Risks & Mitigations:** Administrative discipline overhead; mitigated by pre-configured GitHub Issue templates.

#### AI Agent Guardrails
- *When prompted to decompose tasks or create issue drafts, the AI agent MUST strictly adhere to the schema specified in `.github/ISSUE_TEMPLATE/use-case.md`.*
- *Every module or version referenced by the agent must conform to the established SemVer structure.*

## 4. Summary of Project Operational Assumptions & Heuristics

For project planning, cost calculation, and scheduling under the Unified Process, the following operational assumptions are codified:

1. **Unitary Mapping:** $1\text{ Functional Requirement (FR)} \leftrightarrow 1\text{ Use Case (UC)} \leftrightarrow 1\text{ Iteration} \leftrightarrow 1\text{ Maven Submodule} \leftrightarrow 1\text{ SemVer Target Release}$.
2. **Standard Working Week:** Defined as 40 billable professional hours per human consultant.
3. **Baseline Human Resource Costs:**
   - **Iteration 0 (Inception Phase):** Fixed baseline estimate of €1,000 (human labor).
   - **Iteration $N$ (Transition Phase):** Fixed baseline estimate of €2,000 (human labor for system integration, deployment packaging, and manual authoring).
4. **Tooling and AI Model Budgeting:**
   - Account for tooling licenses and token allowances (GitHub Campus Program / GitHub Copilot for Students at zero cost; Google AI Pro / Gemini student tiers; or local open-weight runtimes via Ollama / LM Studio).
   - Evaluate the impact of model parameter scale and code domain specialization on development productivity and human review overhead.
5. **Human-AI Latency Buffer:** Project schedules must realistically account for latency incurred while AI-generated code awaits human cognitive review, verification, and merge approvals, discounting model optimism bias.
